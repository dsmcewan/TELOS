## Item 1 — Caps (challenge round cap default 4 / code-produce round cap default 8)

### What is actually at stake

The design doc's "Call accounting (bounds)" table (`docs/superpowers/specs/2026-07-20-daedalus-workflow-v2-design.md:705-717`) proposes two named constants that do not yet both exist: `ADVERSARIAL_MAX_ROUNDS` / `CODE_REVIEW_MAX_ROUNDS` for the challenge stages (default 4) and `CODE_MAX_ROUNDS` for Stage 3 code-produce (default 8). These read as a matched pair in the doc, but they are not symmetric in evidentiary status. One of them is already load-bearing, tested code; the other names a mechanism — Stage 3 code-produce friction between Seats 1∥2 — that has zero lines of implementation anywhere on disk. Ruling on them as if they were equally mature would ratify a real number and an invented one under the same vote. The cap value also silently feeds item 7's cadence formula (`⌈cap/2⌉` per the chair's ruling there), so changing either default here re-tunes a threshold that item 7 already fixed against the current values.

### Evidence: what is actually shipped

**The challenge cap (4) is already implemented, not merely proposed.** `docs/runs/production-profile-compiler-1-workshop/daedalus-v2.mjs:344` defines `maxChallengeRounds = 4` as the literal default parameter to `runDaedalusV2`, and the Stage 2 loop at `daedalus-v2.mjs:482` (`for (let round = 1; round <= maxChallengeRounds; round += 1)`) enforces it as a hard global ceiling — round counters are explicitly documented as never reset by defend, modify, or re-entry (`daedalus-v2.mjs:478-479`, matching the design doc's own claim at line 716-717). Two tests exercise this directly: Case 14 (`test-daedalus-v2.mjs:407-420`) drives 5 denied rounds against `maxChallengeRounds: 4` and asserts `result.reason === "challenge-round-cap"` with exactly 4 rounds recorded; Case 29 (`test-daedalus-v2.mjs:765-778`) proves a `modify` re-entry does not reset the counter, using `maxChallengeRounds: 2`. So "4" is not an undemonstrated design-doc number — it is the value already chosen, coded, and tested in the one stage of v2 that exists.

**The code-produce cap (8) has no implementation to inherit.** A repo-wide search finds zero occurrences of `CODE_MAX_ROUNDS` or `CODE_REVIEW_MAX_ROUNDS` outside the design doc itself. `daedalus-v2.mjs` is 731 lines and covers Stage 0 (research breakout), Stage 1 (plan produce, via injected `runJoin`), and Stage 2 (plan challenge) only — there is no Stage 3 (code produce) or Stage 4 (code challenge) function, loop, or call site anywhere in the file. `test-daedalus-v2.mjs`'s 30 cases cover research survivors, plan-produce disposition, the challenge-round cap, denied-twice, oscillation, referee cadence/burn, and provenance rules — none exercise a code-produce round or a code-round cap. Item 7's exemplar brief independently confirms this from the referee side: "The 8-round produce loop, where a semantic watcher would actually earn its call, has no referee call site at all. Produce-side cadence is specified and unimplemented" (`item-7-referee-ruling-packet.md:30`). Item 1's cap and item 7's cadence are pointing at the same hole: Stage 3 does not exist yet.

**A same-numbered but structurally different precedent exists nearby.** `build-gate/proposal-orchestrator.mjs:148` sets `maxRepairRounds = 8` as the default threaded into `runBuild({ ..., maxRounds: maxRepairRounds, ... })` at `proposal-orchestrator.mjs:216` and `:313`. This is a real, shipped "8" in the currently-live proposal-lifecycle execution path — but it bounds a different mechanism: `runBuild`'s round is one dispatch wave over the whole DAG's ready-node frontier (`merkle-dag/orchestrate.mjs:190-224`, `for (let round = 0; round < maxRounds; round++) { ...const ready = readySet(...); if (ready.length === 0) break; ...}`), not a Seats-1∥2-vs-Seats-3+4 friction round over one candidate. `runBuild`'s own function default is in fact `maxRounds = 1000` (`orchestrate.mjs:190`) — a cost fuse, not a considered bound; 8 is a caller-chosen tightening specific to the proposal-lifecycle path. It is suggestive that "8" is not a number pulled from nowhere in this codebase's execution layer, but it is not direct evidence for a Stage-3 friction-round cap, because the unit being capped is different (DAG-wave count vs. produce/challenge friction round count). Other same-repo caps point the opposite direction on scale: `build-gate/daedalus.mjs:15`'s `DAEDALUS_MAX_ROUNDS = 6` bounds the legacy (currently shipped, non-split) single-loop planning workshop; `breakout/breakout.mjs:30-32` defaults to 3 rounds without a referee and 12 with one (explicitly a "cost fuse, not the governing bound" once a referee is wired — `breakout.mjs:23-24`); `saas-forge/breakouts.mjs:42` also defaults to 3. None of these is the same mechanism as v2's split produce/challenge stages, but together they show this codebase's institutional habit is tight caps (3–6) for single-loop challenge/produce cycles, with looser numbers reserved for DAG-wave or referee-backed fuses. An 8-round friction cap for Stage 3 — a stage that does not yet exist — sits at the loose end of that range with no run-time evidence behind it at all.

### Option A — Ratify both defaults as fixed protocol constants, as proposed (4 / 8)

**The case for it.** Symmetry and forward motion: the doc already writes both numbers into one table, and ratifying both now means Stage 3's eventual implementation has a pre-approved bound to code against instead of blocking on a second Eye ruling later. 4 is already correct by the evidence above, so ratifying it costs nothing.

**The case against.** It rules on a mechanism that doesn't exist as if it were measured. There is no fixture, no dogfood run, no test — nothing analogous to the challenge-cap's Case 14/29 — showing that 8 code-produce rounds is enough to let real Seats 1∥2 code-level friction converge, or so loose that it burns 8 rounds of paired-model calls (2 seats × N sub-calls per round, per the "Call accounting" table's own accounting) before a stalled loop reaches the Eye. The nearest same-repo analogue (`maxRepairRounds = 8`) bounds a different unit (DAG-wave, not friction round), so it cannot be read as validating this number for this mechanism.

**What it costs.** Nothing to ratify 4. Ratifying 8 costs an unfalsifiable commitment: if Stage 3 ships and 8 turns out to be badly calibrated (too tight — the produce pair never gets tests green; too loose — cost blowout before a stalled loop reaches the Eye), reopening the number requires a fresh Eye ruling anyway, so nothing was actually saved by pre-approving it.

**What breaks if it is wrong.** If 8 is too loose: a genuinely stuck Stage 3 loop burns up to 8 rounds of paired-seat calls (with no referee call site to shorten it early, per item 7's finding) before `needs-work` fires — pure cost, no safety exposure, since `needs-work` still grants nothing. If 8 is too tight: real, still-converging code work gets forced to `needs-work` and an Eye action is spent reopening a stage that only needed a few more honest rounds — the scarce-resource cost item 7 already named for early terminals.

### Option B — Ratify 4 as fixed; leave 8 provisional and Eye-tunable per run until Stage 3 ships with evidence

**The case for it.** It treats the two numbers according to their actual evidentiary status instead of pretending symmetry. 4 gets ratified because it is already running code with passing tests behind it (`daedalus-v2.mjs:344`, `test-daedalus-v2.mjs` Cases 14/29) — there is nothing left to prove. `CODE_MAX_ROUNDS` gets treated as a placeholder parameter, not a settled literal: implementers ship Stage 3 with it as an explicit, overridable field (not a hardcoded number baked into a loop condition), and the Eye reserves the right to set or move its default per run once a handful of real Stage-3 runs exist to look at — mirroring exactly how item 7 deferred the referee-model question to "when the counters produce data" rather than ruling on an untested claim now. (What that default should actually be — 8, something in this codebase's 3-6 single-loop-cap range, or no single number at all — is a separate question, addressed in "Recommended ruling" below, that the tunability mechanism itself does not resolve.)

**The case against.** It leaves an open number in the design, and "Eye-tunable per run" is itself a governance surface that has to be specified (who can set it, is it in the frozen requirement frame, does changing it mid-run require a new Eye gate) — work this ruling would be deferring rather than doing. It also means Stage 3's first implementer has one more knob to justify instead of a settled number to build against.

**What it costs.** A second, smaller ruling later (or a standing default-with-override policy) once Stage 3 exists. This is not free reuse of an existing path: checked against every current call site, neither `maxChallengeRounds` nor `maxRepairRounds` is ever populated from the dossier — each is a caller-supplied parameter with a code default (`daedalus-v2.mjs:344`, `proposal-orchestrator.mjs:148`), but every call site that sets one hardcodes a plain JS literal (`maxChallengeRounds: 4` or `2` in `daedalus-v2.mjs`/`test-daedalus-v2.mjs`; `maxRepairRounds: 20, 12, 6, 5, 3` across `build-orchestrator.mjs`/`proposal-orchestrator.mjs` callers and their tests) — none is threaded from a dossier/config field. The actual precedent for dossier-to-parameter wiring sits one parameter over, in the very same function: `maxRevisions` is read from `dossier?.max_revisions` at `proposal-orchestrator.mjs:200`. So a per-run dossier override for `CODE_MAX_ROUNDS` would follow an idiom that exists in this codebase (`maxRevisions`'s pattern), but it is net-new plumbing for *this* parameter, not something `maxChallengeRounds`/`maxRepairRounds` already do — the earlier framing overstated how costless this option is.

**What breaks if it is wrong.** Nothing new breaks relative to Option A — the failure modes (cost blowout vs. premature `needs-work`) are identical. What changes is that the number can be corrected without needing to re-litigate whether it was ever evidenced, because it was never claimed to be.

### Fixed constant vs. Eye-tunable — direct answer

Both defaults should be **code constants with caller-overridable defaults**, not baked-in literals — this is already the codebase's convention, not a new ask: `maxChallengeRounds` (`daedalus-v2.mjs:344`), `maxRepairRounds` (`proposal-orchestrator.mjs:148`), and `maxRounds` in `breakout.mjs`/`saas-forge/breakouts.mjs`/`forge/ratchet.mjs` (which additionally reads `TELOS_MAX_ROUNDS` from the environment, `ratchet.mjs:231-232`) are all parameters with sensible defaults, never hardcoded inline round-counting. There is no reason for `CODE_MAX_ROUNDS` to be the one exception that hardcodes 8 with no override path. The question of whether The Eye can change the *default* mid-project (not just override per call) is a governance-process question, not an implementation one, and nothing here argues for making that harder than it already is for the other caps.

### The item-7 coupling — this is a real, already-latent bug, not a hypothetical

This is not a theoretical risk to flag defensively; it is already sitting in the shipped code. `daedalus-v2.mjs:34` defines `const REFEREE_MIN_CHALLENGE_ROUND = 2;`, a bare literal, and it is used at `daedalus-v2.mjs:583` (`if (round >= REFEREE_MIN_CHALLENGE_ROUND ...)`) to gate when the referee is first consulted in Stage 2. It is **not** computed as `Math.ceil(maxChallengeRounds / 2)` — it is independently hardcoded to `2`, and it only happens to equal `⌈4/2⌉` because both numbers were chosen together and never revisited. If item 1 moves the challenge cap away from 4 (say, to 6 for extra friction headroom), `REFEREE_MIN_CHALLENGE_ROUND` stays `2` unless a second, separate edit updates it — silently breaking item 7's ⌈cap/2⌉ ruling without either ruling's text changing. Any disposition of item 1 that changes the challenge-cap default from 4 **must** carry an explicit instruction to also change `daedalus-v2.mjs:34`'s literal (or, better, replace it with a derived `Math.ceil(maxChallengeRounds / 2)` expression at that call site) in the same change — otherwise the two rulings drift apart on disk while agreeing on paper. This is exactly the class of defect item 7's own text warned about ("open item 1 can move the caps — which would silently re-tune item 7," `item-7-referee-ruling-packet.md:28`), now confirmed concretely at a line number rather than argued abstractly.

### Recommended ruling

**Ratify 4 as the fixed challenge-round-cap default (Option A for that half only) — it is already shipped, tested code, not a proposal. On the produce-side cap, rule only the mechanics, not the value: `CODE_MAX_ROUNDS` (or whatever bounds Stage-3 produce work) must ship as an explicit, overridable parameter in the same idiom as `maxChallengeRounds` and `maxRepairRounds` — a named field with a coded default, never an inline literal — and decline to ratify a specific default number for it right now.** This narrows Option B rather than abandoning it: the tunability half of Option B still holds, but the packet's earlier "default to 8" position does not survive its own cited evidence and is withdrawn here in favor of flagging the value as genuinely open.

The single strongest reason to ratify 4 now, unchanged from the original analysis: the two numbers are not evidentiary peers — one has Cases 14 and 29 behind it and the other has zero lines of the mechanism it would bound anywhere on disk, and item 7's own brief already found the identical hole from the referee side ("no referee call site at all" for the 8-round produce loop). Treating them as a matched pair to ratify in one motion launders an untested number under the credibility of a tested one.

The single strongest reason to withdraw the "default to 8" recommendation: this packet's own "Evidence" section states the codebase's institutional habit is tight caps (3-6) for single-loop challenge/produce cycles, with looser numbers reserved for DAG-wave or referee-backed fuses — provisionally defaulting a single-loop produce cap to 8 sits outside that stated range, and no argument reconciling the two was ever supplied. Worse, it is not settled that "the Stage-3 produce cap" even names one mechanism to default. Item 4's sibling packet (`item-4-stage3-team-leads-ruling-packet.md`) argues — and recommends, as its own Option C — that Stage 3 as actually built is team-lead dispatch (`teamForNode`/`runBuild`) already bounded for ordinary nodes by the shipped `maxRepairRounds = 8` and `adaptAttempts = 2` (`proposal-orchestrator.mjs:148,313`), with literal Seat-1/Seat-2 dual-pressure friction reserved only for nodes named in the Stage-1 obligation matrix's `discharge_node_id` set. If The Eye adopts item 4's Option B or C, most Stage-3 nodes need no new `CODE_MAX_ROUNDS` at all — they are already governed by a real, shipped, differently-sourced cap — and only a narrow discharge-node friction path, if any, would need a genuinely new round cap, for which the 3-6 institutional habit is the defensible reference class, not `maxRepairRounds`'s DAG-wave 8. Item 1 cannot responsibly pick a single produce-cap number while item 4 is still open on what "the produce cap" bounds — doing so risks ratifying a number for a mechanism that may not exist in the shape assumed.

As a mandatory rider on ratifying 4 (not an alternative to it): direct that `daedalus-v2.mjs:34`'s `REFEREE_MIN_CHALLENGE_ROUND = 2` literal be replaced with a derived `Math.ceil(maxChallengeRounds / 2)` at the Stage 2 call site, so a future change to the challenge cap cannot silently desync item 7's cadence ruling the way it would today.

**This recommendation resolves into a specific produce-cap number once item 4 is ruled, not before.** If The Eye adopts item 4's Option A (literal dual pressure on every node), the produce cap is a real per-node friction-round bound and belongs in the 3-6 institutional-habit range absent contrary evidence — not 8. If The Eye adopts item 4's Option B or C (team-lead default), most nodes are already bounded by the shipped `maxRepairRounds = 8`/`adaptAttempts = 2` and need no separate `CODE_MAX_ROUNDS`; only Option C's carved-out discharge-node friction path would need a new, narrow cap, again against the 3-6 range rather than 8. An 8-based default for `CODE_MAX_ROUNDS` survives this analysis only if The Eye independently judges `maxRepairRounds = 8`'s DAG-wave semantics close enough to whatever friction-round semantics item 4 lands on to count as precedent rather than coincidence — that judgment call remains open and available to The Eye, but it is no longer this packet's lead recommendation given the unreconciled 3-6 contradiction and the unresolved item-4 dependency.
