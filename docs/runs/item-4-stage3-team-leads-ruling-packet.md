## Item 4 — How tightly Stage 3 maps to parallel dual seats vs team-leads under the DAG

### What is actually at stake

Stage 3's own text tries to reconcile two mechanisms that already exist on disk, already diverge, and today are wired together with **no code-level friction step between them at all**. `runParallelDaedalus` (`build-gate/daedalus.mjs:311-351`) is a **whole-frame, single-round** parallel-authorship join: two seats each produce one source node, one integrator produces one candidate that must `descends_from` exactly both, two verifiers attest preservation, and `deriveParallelState` returns one verdict for the whole candidate. It has no concept of a DAG node, a topo position, or "node-by-node" iteration — it does not decompose at all. Separately, `teamForNode` (`build-gate/teams.mjs:81-89`) + `runBuild` (`merkle-dag/orchestrate.mjs:190-279`) is the **actual node-by-node-in-topo-order** executor already in production: `readySet` (`orchestrate.mjs:68-74`) computes the topo-respecting frontier, `criticalWeights` (`orchestrate.mjs:78-92`) schedules it, and each ready node is dispatched to exactly one owning team whose **lead alone** emits the files (`teamPrompts.mjs:52,100` — "team's buildable lead... asked to emit the node's files"; the roster's `member` seats are declared for composition/prompting rationale, not co-authorship at dispatch time). This is single-writer-per-node, not dual-pressure.

The current autonomous entry point has already picked a side, and it isn't Stage 3 as written. `proposal-orchestrator.mjs:210-211` calls `runParallelDaedalus`/`runDaedalusWorkshop` **once per revision, over the whole candidate task list** — that is the plan-level friction (Stage 1's analogue). Then, on `decision === "authorized"`, `proposal-orchestrator.mjs:308-317` calls `runBuild` with `dispatch: makeTeamDispatch({ routeFor: (id) => routeForNode(id, allTasks, teams), ... })`, and `routeForNode` (`proposal-orchestrator.mjs:341-344`) is a thin wrapper over `teamForNode`. **There is no code-level Seat-1/Seat-2 friction call site anywhere in the shipped path.** Confirmed by absence: `CODE_MAX_ROUNDS`, `ADVERSARIAL_MAX_ROUNDS`, and `CODE_REVIEW_MAX_ROUNDS` — the three constants Stage 3/4's own call-accounting table (design doc lines 705-714) names as bounds — do not exist anywhere in the repo (`grep` for all three across every `.mjs` file returns nothing). Stage 3-as-friction is pure design; Stage-3-as-team-dispatch is what's built, tested, and evidenced three times over (`docs/runs/agentic-teams/`, `agentic-teams-market/`, `agentic-teams-situational/`, per `contracts/Agentic Teams Autonomous Builder.md:160-176`).

One more disambiguation the design doc itself risks blurring: "Rule 1 isolation" is not "one writer per file." The canonical Rule 1, defined at `contracts/Agentic Teams Autonomous Builder.md:22` and enforced at `orchestrate.mjs:149-156`, is the **spec-injection boundary** — a dispatched worker sees only `{id, requirements, files, test, effective_hash}`, never the rest of the plan or another node's context. "One writer per file" is a *separate*, weaker, advisory property: `planner.mjs:49-62` detects write-write conflicts and, outside `strict` mode, only emits an advisory string (`"only the LAST writer can pass ledger-gate... Prefer one writer per file"`) — it does not block. The actual concurrency guard against two workers touching the same file **at runtime** is `orchestrate.mjs:223-231`'s write-disjoint batch filter, which defers (not rejects) overlapping ready nodes to a later round. So today, one-writer-per-file is enforced at the scheduler level (never concurrently), not at the plan-compile level (never at all, absent `strict`). Item 4's ruling should not assume "Rule 1 isolation" already means one-writer-per-file; it means the narrower spec-injection guarantee, which both Option A and Option B already satisfy by construction (`runOne` at `orchestrate.mjs:150-156` for team dispatch; `runParallelDaedalus`'s per-seat `callSeat({ seat, role, phase, frame, sources })` calls at `daedalus.mjs:315,328,344` for parallel authorship — each seat call is scoped to its role, not handed the other seat's raw internals).

### Option A — literal Seat-1/Seat-2 dual pressure on every Stage 3 node

**The case for it.** It is the reading that matches the Goal table's blanket claim (design doc line 24) that "dual-seat friction" mitigates hallucination, and it would give code-grain friction its own escalation-to-Eye path (`deriveParallelState`'s `conflict` → `needs-eye` terminal, `daedalus.mjs:298`, already wired for `violated` verifier verdicts) exactly where hallucinated code is most likely to originate — at the point of writing it, not later at whole-tree challenge. It requires no new state machine; `runParallelDaedalus` already exists and is unit-tested (`scripts/test-daedalus.mjs`) and live-run (`docs/runs/clotho-loader-redesign/run-loader-redesign.mjs:238`, invoked over one frozen frame there too).

**The case against.** Nothing on disk runs `runParallelDaedalus` per DAG node, and its shape resists that reuse without rework: one call produces **one** candidate descending from **exactly two** source refs (`deriveParallelState`, `daedalus.mjs:270-272`) and requires **five real, pairwise-distinct provenance keys** per invocation (`daedalus.mjs:286-289`). Repeating it per node multiplies provider calls by roughly 5×(node count) for a single Stage-3 pass, and every produce-cycle retry after a Stage-4 deny or a floor failure (design doc lines 654-660) multiplies again — a cost dimension the design doc's own call-accounting table doesn't appear to have priced: it states Stage 3 as "≤ `CODE_MAX_ROUNDS` (default 8) produce cycles" (line 712) with no `× node count` term, reading like the single-round-over-the-whole-artifact shape Stage 1 already uses, not a per-node multiplier. There is no evidence anywhere — no test, no run script, no comment — that anyone has scoped what "5 keys × N nodes × up to 8 rounds" costs or whether providers/timeouts tolerate it.

**What it costs.** Net-new wiring: `runParallelDaedalus` (or a variant) called once per topo-order node instead of once per plan; a new per-node obligation-matrix shape (today's matrix is plan-grain — `validateObligationCoverage`, `daedalus.mjs:219-231` — not node-grain); and an unknown multiple of provider spend that scales with plan size, which cuts directly against "smallest complete behavioral model" (design doc line 199) since bigger plans no longer decompose into cheaper pieces — they decompose into more expensive ones.

**What breaks if it is wrong.** Every plan above a handful of nodes becomes prohibitively slow/costly to build, which creates exactly the perverse incentive the planner's write-write-conflict granularity and Rule-1 isolation are meant to avoid: operators coarsen tasks into fewer, larger nodes to dodge the per-node friction tax, which is worse for auditability (bigger diffs per settlement, harder Rule-3 attribution) than the fine-grained DAG the merkle substrate was built for.

### Option B — team-lead dispatch on every Stage 3 node (status quo, unweakened)

**The case for it.** This is what is actually built, tested, and run to `merge_status: "ready"` three separate times (`docs/runs/agentic-teams*`, per `contracts/Agentic Teams Autonomous Builder.md:160-176`). It is *already* "node-by-node in topo_order": `readySet`/`criticalWeights` (`orchestrate.mjs:68-92`) and the per-round batch loop (`orchestrate.mjs:214-251`) are precisely that mechanism. It composes for free with the friction that already exists on both sides of it — Stage 1's whole-plan dual-seat join happens *before* any node is dispatched (obligations and constraint ownership are settled at plan grain), and Stage 4's whole-tree challenge happens *after* every node settles, so team-lead execution is bracketed by friction rather than lacking it entirely. Cost per node is small and bounded: one lead call plus up to `adaptAttempts` (default 2, per `contracts/Agentic Teams Autonomous Builder.md:121`) self-correction retries, not a 5-key round.

**The case against.** Between the two friction brackets, an individual node's code is authored by exactly one seat and checked only by Rule 3's mechanics — disk tree hash plus that node's own test (`orchestrate.mjs:121-138`, `defaultVerifyNode`). If that test is shallow, or the hallucination happens to satisfy it, nothing at node grain catches it; the defect surfaces only at Stage 4's whole-tree challenge, which then has to attribute a tree-level objection back to one node and return the **entire tree** to Stage 3 as friction (design doc lines 664-673) — a coarser, later catch than the Goal table's claim that dual-seat friction is *the* hallucination mitigation (line 24) would suggest applies uniformly.

**What it costs.** Nothing new — this is the shipped path.

**What breaks if it is wrong.** A single-seat-authored node with a hallucinated or drifted implementation that happens to pass its own declared test rides through Stage 3 unchallenged until Stage 4 catches it at tree grain (if Stage 4 is ever implemented — today it isn't either; see "What is actually at stake"). The failure is quiet in exactly the way `docs/runs/agentic-teams-situational/` demonstrates the *opposite* case is handled (a team self-correcting on its own test failure) — a test that doesn't fail gives no signal to self-correct against.

### Option C — hybrid: team-lead default, dual pressure mandatory on obligation-discharge nodes (recommended)

**The case for it.** The boundary is not a node-count or plan-size guess — no evidence on disk supports any particular number, and picking one would be exactly the kind of ungrounded, mutable threshold the project's content-address rule warns against keying an enforcement decision on. The alternative boundary is already a computed, hashed fact: `attachObligations` (`merkle-dag/obligation.mjs:72-120`) names each obligation's `discharge_node_id` at Stage-1 compile time, and that id set is part of `plan.obligations`, which is folded into `plan_hash` (`compileAndHashPlan`, `planner.mjs:92`) — it cannot be relabeled after the fact without changing the plan's identity. A controller predicate "is `node.id` a discharge node?" is therefore a content-addressed membership test, not a size heuristic. This concentrates the expensive 5-key friction exactly where the project's own obligation matrix has already flagged invariant-bearing work — which is where Stage 0/1's Surface B (production envelope) and the constraints seat's proof-obligation ownership (design doc lines 179-181) actually need code-grain pressure — while leaving the bulk of ordinary, non-obligation-bearing nodes on the cheap, already-built, already-evidenced team-lead path. That is the intended shape of the boundary — which nodes the plan has already flagged as invariant-bearing, a content-addressed fact rather than a size guess. Whether the friction actually lands on those nodes *as currently wired* is a separate question: "The case against" and "What it costs" below show the live routing does not yet point at the authoring node, only at a synthetic check node. That wiring gap does not weaken the case for using obligation-discharge membership, rather than a node count, as the selection criterion — it is a cost/readiness problem, addressed below, not a flaw in the boundary itself. It also reuses two escalation paths Stage 3 already specifies rather than inventing a third state machine: "floor failure after agreement" (same tree hash failing twice → `needs-work`, design doc lines 654-657) and "deny from Stage 4 returns here as friction" (line 660) both already describe a node moving from cheap execution into dispute; Option C just makes obligation-discharge nodes start there instead of escalating into it.

**The case against.** A single stage now has two execution modes, so the call-accounting table (design doc lines 705-717) needs a second row (or an explicit split) instead of one bound for "3 code produce" — today's table reads as if Stage 3 were uniform, and a mixed-mode stage is harder to audit as "a hard derivable ceiling per run" (line 717) without that split. It also inherits Option A's un-costed multiplier, just scoped down to however many nodes the obligation matrix names — if Stage 0/1 under-declares which nodes are invariant-bearing, those nodes get the cheap path by omission. This is not a *new* hole Option C opens, though: `validateObligationCoverage`'s bijection check (`daedalus.mjs:219-231`) already exists to catch a matrix that drops or fabricates obligation coverage at Stage 1, before any code exists — Option C rides on a check that's already load-bearing rather than adding a new trust boundary.

There are also two deeper problems, independent of matrix calibration, with treating Option C's two call targets as ready-made rather than requiring new work — both are confirmed against the current code, and both were previously absent from this packet's accounting. **First, a contract mismatch.** `dispatch(injected)` (`build-orchestrator.mjs:52-96`, `orchestrate.mjs:150-179`) has a hard contract: it must return `{ok:true, signer}` after writing `files:[{path,content}]` to disk, which `defaultVerifyNode` (`orchestrate.mjs:121-138`) independently re-hashes for Rule 3. `runParallelDaedalus` (`daedalus.mjs:311-351`) produces a plan/obligation_matrix-bearing candidate with `descends_from` provenance over two source refs — a plan-authorship artifact with no `files` array and no per-node `effective_hash` concept. Every real invocation of `runParallelDaedalus` in the repo (`scripts/test-daedalus.mjs`, `docs/runs/clotho-loader-redesign/run-loader-redesign.mjs`, `docs/runs/production-profile-compiler-1-workshop/workshop-lib.mjs`, and `proposal-orchestrator.mjs`'s own Stage-1 usage) treats its output as one markdown/text blob, never as per-file `{path,content}` writes — the clotho run's own header states the deliverable is a redesigned spec section, "NOT code." This is the identical incompatibility Option A's "case against" and "what it costs" already charge as a real, uncosted engineering item when discussing reusing `runParallelDaedalus` at node grain; Option C relies on the same function and inherits the same gap, not a smaller version of it. **Second, a predicate misfire.** The one live path that produces `discharge_node_id` values, `mintVerificationNodes` (`proposal-orchestrator.mjs:76-99`), always mints a brand-new synthetic node with `writes:[]` and a fixed `check-registry.mjs` whitelist template as the discharge node — confirmed at `proposal-orchestrator.mjs:96`, where `discharge_node_id` is set to `nodeId`, the freshly-minted verification node's own id, and by grep: no other live (non-test-fixture) call site in the repo populates the field. So the controller predicate "is `node.id` a discharge node?" would, wired as today's code stands, route the expensive friction onto empty check-runner shells, not the real implementation node whose hallucination risk motivated the option — the opposite of concentrating friction where invariant-bearing work happens.

**What it costs.** One controller predicate (node id ∈ discharge-node-id set, computed once per plan) plus an explicit per-node router that does not exist today — `routeForNode` (`proposal-orchestrator.mjs:341-344`) always calls `teamForNode`; it would need a companion branch that routes dual pressure instead when the predicate is true. That branch is **not** a drop-in reuse of `runParallelDaedalus`, and the earlier framing here — "no new seat wiring: both call targets already exist" — does not hold: the two functions exist, but their contracts don't compose, and the one live source of `discharge_node_id` values names the wrong node. Making Option C real costs two things this packet previously left uncosted:
1. **A genuine adapter** — a new integrator/verifier output schema, prompt changes, and multi-file handling to convert `runParallelDaedalus`'s converged plan-text into the `{files:[{path,content}]}` shape `dispatch` requires so `defaultVerifyNode` can re-hash it for Rule 3. This is comparable in kind to the engineering item the packet already itemizes in detail for Option A's reuse of the same function — not a cheaper version of it, just one built once and then applied to fewer node-invocations per run.
2. **A discharge-node routing fix** — `mintVerificationNodes` must be changed (or a second minting path added) so `discharge_node_id` can name the actual code-authoring node an obligation is about, not only the synthetic, empty (`writes:[]`) check node it mints today. Without this, Option C's predicate fires on the wrong node regardless of whether item 1 is built.

Item 1's per-invocation cost still scales with the (hopefully much smaller) discharge-node set rather than every node, which is the real basis for preferring Option C's operating cost over Option A's — but that comparison assumes item 1 exists, and nobody has scoped how large it is.

**What breaks if it is wrong.** This paragraph describes calibration risk once the adapter and routing fix above exist and the predicate actually reaches the authoring node — a distinct question from whether the boundary is well-chosen. If the obligation matrix is thin (few discharge nodes) relative to where real risk lives, Option C degenerates toward Option B's failure mode for everything outside that thin set — quiet single-seat hallucination surviving to Stage 4 grain. If it is over-broad, it degenerates toward Option A's cost multiplier. Either failure is visible and correctable by tightening or loosening Stage 1's obligation coverage — it is not a silent, unrecoverable failure mode, because the boundary is the same hashed structure the gate already audits.

### Recommended ruling

**Adopt Option C's boundary logic, as a conditional target rather than a settled, ready-to-ship design: Stage 3 defaults every node to the existing team-lead dispatch path (`teamForNode` + `runBuild`, already built, already evidenced three times), and requires literal Seat-1/Seat-2 dual pressure only on nodes named as `discharge_node_id` in the Stage-1 obligation matrix — a content-addressed, already-hashed membership test, never a node-count or plan-size guess.** That boundary-selection argument is untouched by the two problems found in this packet's earlier costing and is still the strongest reason to prefer C's *shape* over A's or over any manually-picked hybrid cutoff: obligation-discharge membership is a fact the plan already commits to at `plan_hash` (`compileAndHashPlan`, `planner.mjs:92`) before Stage 3 ever runs, whereas Option A's uniform application needs an un-costed per-node multiplier nobody has measured, and any node-count boundary for a hybrid would be exactly the kind of mutable label the project's core invariant forbids keying an enforcement decision on.

What is no longer true, and must not be carried forward as settled, is the earlier claim that this costs "no new seat wiring" because "both call targets... already exist." Two corrections, detailed under Option C's "The case against" and "What it costs," change this from an unconditional ruling to a conditional one:

1. **Contract mismatch.** `runParallelDaedalus` produces plan-text with `descends_from` provenance, not the `{files:[{path,content}]}` shape `dispatch` must return for `defaultVerifyNode` to re-hash under Rule 3. A real adapter — new integrator/verifier output schema, prompt changes, multi-file handling — is required, and it is comparable in kind to the engineering item this packet already charges to Option A, not a cheaper substitute for it. Building it once and applying it only to discharge nodes still costs far less in ongoing provider spend than Option A's blanket per-node application, so the relative cost ordering (C cheaper to *operate* than A) survives — but the one-time build is not zero, and this packet has not scoped it.
2. **Predicate misfire.** The only live path that mints `discharge_node_id` values (`mintVerificationNodes`, `proposal-orchestrator.mjs:76-99`) always names a synthetic, empty (`writes:[]`) check node, never the code-authoring node whose obligation it discharges. Making dual pressure land where Option C intends — on the invariant-bearing implementation node, not a check-runner shell — requires a routing fix that does not exist today. Option A needs no equivalent fix, since it never consults `discharge_node_id`.

Neither correction changes which option's *shape* is structurally preferable once both pieces of engineering exist; both change whether Option C can be adopted as-is today. The honest ruling this packet can make is: **commit to Option C's boundary (discharge-node membership, not a size guess) as the target design, and carry the adapter (item 1) and the discharge-node routing fix (item 2) forward as required, currently-uncosted scope of that commitment** — not as already-available machinery, and not as a reason to defer the decision indefinitely. The Eye should treat the size of that combined engineering item as an open question this packet cannot answer from evidence on disk today; if it turns out large enough to erode Option C's operating-cost advantage over Option A (for instance, if the adapter ends up duplicating most of what Option A would need anyway, or if the real obligation-matrix density turns out to leave little cost-scoping benefit), that is grounds to revisit, not evidence already in hand here.

This flips toward Option A (dual pressure on every node, cost accepted) if The Eye rules that the Goal table's "dual-seat friction mitigates hallucination" (design doc line 24) must hold literally and uniformly at code grain regardless of cost — i.e., that Stage 4's whole-tree challenge bracket is not an acceptable substitute for per-node pressure on non-obligation nodes — in which case the adapter (item 1) must be built regardless of which option ships, and Option A's uniform routing avoids paying for item 2 at all. It flips toward Option B (team-lead only, no hybrid) if The Eye rules that Stage 4's code challenge — once actually implemented, since it does not exist today either — is sufficient friction on its own, or judges that the now-uncosted adapter-plus-routing-fix item is not worth committing to for a boundary this packet cannot yet show is well-calibrated to real invariant-bearing risk (see Option C's "What breaks if it is wrong").
